# История просмотров MrBeast

Приложение на TypeScript собирает **число просмотров** публичных видео каналов [MrBeast](https://www.youtube.com/@MrBeast) и [MrBeast Gaming](https://www.youtube.com/@MrBeastGaming) через официальный YouTube Data API v3. Первый сбор выполняется сразу после запуска, последующие — **каждые 5 минут для каждого канала**. История сохраняется в общей SQLite. В карточке каждого видео показаны канал и дата публикации с временем в часовом поясе браузера. Веб-интерфейс показывает фактические просмотры и аппроксимирующую функцию на одном графике, сравнение прироста и экстраполяцию в будущее.

Видео отслеживается, пока его возраст меньше `TRACKING_WINDOW_DAYS` (по умолчанию **14 дней**). В этот момент новые записи прекращаются. Когда возраст становится **больше двойного срока** (по умолчанию **28 дней с публикации**), удаляются и видео, и все его наблюдения. Ровно на границе хранения данные ещё сохраняются. Очистка выполняется отдельно для каждого настроенного канала перед его циклом, включая циклы со сбоем API. Границы считаются по точным временным меткам UTC, от даты публикации.

## Запуск

Нужен **Node.js 24.19+**; проверенная версия указана в `.node-version`. SQLite встроена в Node.js; отдельный сервер базы данных не требуется. Chart.js включается в локальную сборку интерфейса, CDN не используется.

```sh
npm ci
cp .env.example .env
# Укажите YOUTUBE_API_KEY в .env
npm run build
npm start
```

`npm start` запускает веб-интерфейс и сборщик в одном процессе. Если запускаете на своём компьютере, откройте `http://127.0.0.1:3000`. Это адрес локального запуска, а не публичный адрес среды Codex. Для просмотра уже собранных данных без ключа используйте `npm run web`. Для доступа через сервер настройте `WEB_HOST`, `WEB_PORT`, постоянный диск для `data/` и обратный прокси с HTTPS. Среда Codex не обеспечивает гарантированный непрерывный хостинг: публикация настроек сохраняет подготовленные файлы, а процесс после восстановления нужно запускать заново.

В Google Cloud создайте проект, включите [YouTube Data API v3](https://console.cloud.google.com/apis/library/youtube.googleapis.com), затем создайте ключ в [разделе Credentials](https://console.cloud.google.com/apis/credentials). Ограничьте ключ этим API. Для чтения публичного канала OAuth и вход в YouTube не нужны. Ключ указывается локально в `.env` или в переменных среды хостинга; `.env` исключён из Git. Приложение передаёт ключ в HTTPS-заголовке, а не в URL, и исключает его из сообщений об ошибках.

Для облачной среды разрешите HTTPS-запросы к `www.googleapis.com`. Секрет можно добавить через настройки среды как `YOUTUBE_API_KEY` для этого домена. Команды запуска учитывают `HTTP_PROXY`, `HTTPS_PROXY` и `NO_PROXY` через встроенную поддержку прокси Node.js; проверка TLS остаётся включённой. Во время разработки:

```sh
npm run dev
```

Остановка — `Ctrl+C` или `SIGTERM`. Расписание действует, пока процесс запущен. Для непрерывного сбора на сервере используйте менеджер процессов или сервис хостинга с автоматическим перезапуском и сохраняйте каталог `data/` на постоянном диске. После изменения `.env` перезапустите процесс.

### Установка на свежий VPS Ubuntu/Debian

`scripts/deploy-vps.sh` устанавливает проверенную версию приложения с обоими каналами и Node из `.node-version`, проверяет официальную контрольную сумму Node, выполняет `npm run check` и запускает службу `mrbeast` с автозапуском. База хранится отдельно в `/var/lib/mrbeast/mrbeast.sqlite`. Веб-интерфейс доступен по HTTP на порту 80; для HTTPS позднее нужен домен и обратный прокси. Процесс работает от отдельного пользователя, с разрешением привязать порт 80.

Запускайте установщик **на сервере**, от root, в интерактивном терминале. Для свежего сервера с доступом к GitHub:

```sh
bash scripts/deploy-vps.sh --check  # Только проверки ОС, портов и существующих файлов
bash scripts/deploy-vps.sh
```

Ключ YouTube вводится скрыто в терминале сервера и сохраняется в `/etc/mrbeast/collector.env` с доступом только для root. Он не передаётся в чат и не сохраняется в репозитории. Установщик проверяет успешный сбор отдельно для обоих каналов и ответ локального HTTP API; без этих проверок он не сообщает об успешной установке. Отсутствие недавних видео допустимо после успешных запросов API. В настройках сетевого экрана Timeweb должен быть разрешён входящий TCP 80. Если UFW уже включён, добавляется разрешение 80; сам UFW не включается.

Для передачи исходников без доступа сервера к GitHub задайте `MRBEAST_SOURCE_DIR` с путём к распакованным исходникам. Необязательный `MRBEAST_INITIAL_DATABASE` указывает на согласованную копию SQLite, полученную через backup API; проверяются целостность и структура. Рабочую базу с WAL копировать этим способом нельзя. Без этой переменной сбор начинается с новой истории. Каталог `.env`, рабочие данные и `node_modules` из исходников не переносятся автоматически.

Установщик прекращает работу при занятом порте 80, существующем пользователе `mrbeast` или каталогах установки: существующие приложения и базы не заменяются. Повторный запуск предназначен только для проверки через `--check`; для обновления используйте `update-vps.sh`, как описано ниже. После установки:

```sh
systemctl status mrbeast --no-pager
journalctl -u mrbeast -n 30 --no-pager
systemctl restart mrbeast  # После изменения collector.env
```

Для обновления уже установленного приложения загрузите новую версию репозитория в отдельный каталог на сервере и выполните там от root:

```sh
bash scripts/update-vps.sh
```

Скрипт рассчитан на структуру, созданную `deploy-vps.sh`: сначала устанавливает зависимости и выполняет проверки в отдельном каталоге, затем ненадолго останавливает службу. **До переключения кода** создаётся согласованная резервная копия SQLite через backup API, включая зафиксированные записи WAL; проверяются целостность, внешние ключи и таблицы. Скопировать один рабочий `.sqlite` обычной командой `cp` недостаточно: последние наблюдения могут находиться в WAL.

Рабочая база `/var/lib/mrbeast/mrbeast.sqlite` и ключ в `/etc/mrbeast/collector.env` сохраняются. Копия базы остаётся в `/opt/mrbeast/previous.XXXXXXXX/database.sqlite`, предыдущий код — в том же каталоге `app/`. Каталог доступен только root, старые копии автоматически не удаляются. При ошибке копирования, запуска или HTTP-проверки возвращается предыдущий код и запускается служба; рабочая база при откате не заменяется. Эта версия не меняет схему базы и настройки хранения. Обычная очистка видео старше двойного срока продолжает действовать. Если база перенесена из стандартного пути, скрипт остановится до переключения: сначала нужно проверить фактическую конфигурацию и резервную копию. Если изменён только порт, передайте `MRBEAST_WEB_PORT=3000` (или ваш порт).

Если Git доступен на вашем компьютере, передайте исходники через SCP. **На своём компьютере**, из каталога репозитория (проверьте, что в архив войдут нужные изменения):

```sh
git switch main
git pull --ff-only
git archive --format=tar.gz --output=../mrbeast-update.tar.gz HEAD
scp ../mrbeast-update.tar.gz root@194.87.26.147:/tmp/mrbeast-update.tar.gz
ssh root@194.87.26.147
```

Затем **в терминале сервера**:

```sh
update_source_dir=$(mktemp -d /tmp/mrbeast-update.XXXXXXXX)
tar -xzf /tmp/mrbeast-update.tar.gz -C "$update_source_dir"
MRBEAST_SOURCE_DIR="$update_source_dir" bash "$update_source_dir/scripts/update-vps.sh"
systemctl status mrbeast --no-pager
```

Дождитесь `Update complete`: скрипт также проверит доступность API и нового выбора модели. При недостаточной истории суточная модель может быть недоступна — это нормальный ответ, а не ошибка установки. Откройте страницу с принудительным обновлением (`Ctrl+F5`). Не переносите локальную базу поверх серверной и не запускайте `deploy-vps.sh` для обновления. Архив Git содержит отслеживаемые исходники, без `.env`, базы и `node_modules`. Проверки сборки не останавливают работающий сборщик; перерыв нужен только на резервное копирование, переключение и перезапуск. Для защиты от потери самого VPS отдельно сохраняйте копии базы вне сервера.

## Настройки

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `YOUTUBE_API_KEY` | — | Ключ YouTube Data API v3; необходим для сбора |
| `TRACKING_WINDOW_DAYS` | `14` | Максимальный возраст видео в днях; допустимы положительные дробные значения |
| `POLL_INTERVAL_MINUTES` | `5` | Интервал получения числа просмотров в минутах |
| `FULL_DISCOVERY_INTERVAL_MINUTES` | `60` | Интервал полного обхода списка загрузок канала |
| `DATABASE_PATH` | `./data/mrbeast.sqlite` | Файл SQLite; относительный путь считается от текущей рабочей директории |
| `YOUTUBE_CHANNEL_IDS` | `UCX6OQ3DkcsbYNE6H8uQQuVA,UCIPPMRA040LQr5QPyJEbmXA` | Идентификаторы MrBeast и MrBeast Gaming через запятую; повторы исключаются |
| `YOUTUBE_CHANNEL_ID` | — | Прежняя настройка одного канала, применяется только при отсутствии `YOUTUBE_CHANNEL_IDS` |
| `WEB_HOST` | `127.0.0.1` | Адрес веб-сервера; `0.0.0.0` для доступа через обратный прокси/контейнер |
| `WEB_PORT` | `3000` | Порт веб-сервера |

Если в существующем `.env` задан `YOUTUBE_CHANNEL_ID`, замените его строкой `YOUTUBE_CHANNEL_IDS` из `.env.example`, чтобы собирать оба канала. Новая настройка имеет приоритет. Без обеих переменных собираются оба канала по умолчанию. Обновление не требует миграции базы: прежняя история MrBeast сохраняется.

Значение 14 вынесено в `DEFAULT_TRACKING_WINDOW_DAYS`, множитель хранения 2 — в `RETENTION_WINDOW_MULTIPLIER` в `src/config.ts`. Срок хранения всегда зависит от срока отслеживания: например, 21 день → 42 дня хранения. Изменение срока применяется после перезапуска. Увеличение возобновляет сбор подходящих видео, уменьшение также сокращает срок хранения. Удалённая история и данные за пропущенный период не восстанавливаются.

## Команды и результаты

```sh
npm run collect       # Один сбор и завершение процесса
npm start -- --help   # Справка
npm run check         # Проверка типов, тесты и сборка
```

Каждый успешный цикл канала печатает JSON-сообщение `collection_completed`: `channelId`, `channelName`, время наблюдения, число видео-кандидатов, число сохранённых наблюдений и число пропущенных кандидатов. Ошибки выводятся в stderr с указанием канала; сбой одного не останавливает сбор другого. Разовый запуск проверяет все каналы и при ошибке хотя бы одного завершается с ненулевым кодом. Запросы имеют таймаут и повторяются при сетевых сбоях, HTTP 429 и 5xx. При превышении суточной квоты потребуется дождаться её сброса или увеличить квоту Google Cloud.

Экспорт всей сохранённой истории в CSV не требует API-ключа:

```sh
npm run --silent export > views.csv
```

Колонки: `video_id`, `channel_id`, `title`, `published_at`, `observed_at`, `view_count`. CSV включает всю историю всех сохранённых каналов. Число просмотров хранится как точная целочисленная строка, без округления JavaScript. База содержит таблицы `videos` (метаданные) и `view_snapshots` (история). Записи одного цикла одного канала сохраняются в транзакции; при сбое запроса частичные результаты этого канала не записываются. Повторная запись с тем же видео и временем наблюдения не создаёт дубликат.

## Как работает сбор

1. Для каждого настроенного канала через `channels.list` находится плейлист загрузок; его идентификатор кешируется на время процесса. Каналы имеют независимые расписания и состояние полного обхода в одном процессе.
2. На каждом цикле проверяется первая страница последних загрузок. При запуске и раз в час обходятся **все страницы** плейлиста: порядок загрузок может отличаться от дат публичной публикации. Это позволяет найти свежие видео и за первой страницей. Новая публикация там может быть обнаружена с задержкой до интервала полного обхода.
3. Для найденных видео и уже отслеживаемых видео запрашиваются дата публикации и число просмотров через `videos.list` партиями до 50 идентификаторов. Уже отслеживаемые видео проверяются каждые 5 минут, независимо от полного обхода плейлиста.
4. Перед записью возраст проверяется повторно по `snippet.publishedAt`. Ровно в 14 дней видео исключается. Будущие публикации, предстоящие премьеры, непубличные, удалённые и недоступные видео пропускаются. Shorts и текущие публичные трансляции учитываются, если API возвращает число просмотров.

Значения — те, которые возвращает YouTube API: они могут обновляться с задержкой и иногда уменьшаться после корректировок YouTube. Сервис не восстанавливает историю до первого запуска и не делает предположений о монотонном росте просмотров. Одновременно запускайте один сборщик для одного файла базы.

### Квота

У проекта YouTube Data API обычно есть 10 000 единиц квоты в сутки. Каждое чтение `channels`, `playlistItems` или `videos` стоит 1 единицу; дорогой `search.list` не используется. Квота общая для всего Google Cloud проекта, включая другие приложения; её фактический лимит проверьте в Google Cloud Console.

Для одного канала при `B` партиях статистики (по 50 видео), `P` страницах загрузок, интервале сбора `I` минут и интервале полного обхода `D` минут приблизительный расход за сутки:

```text
ceil(1440 / I) × (1 + B) + ceil(1440 / max(I, D)) × (P − 1) + 1
```

Здесь последняя единица — получение плейлиста канала при запуске. **Расход всех каналов складывается.** Для примера, **20 страниц** и **до 50 отслеживаемых видео** на канал, с полным обходом раз в час: сбор каждую минуту расходует около **3 337 единиц в сутки на канал**, раз в 5 минут — около **1 033**. Для двух таких каналов при пяти минутах получится около **2 066 единиц в сутки**. Это расчёт для примера, а не измеренные размеры каналов. Повторы запросов и частые перезапуски увеличивают расход; если нет подходящих видео, запрос статистики пропускается.

По умолчанию установлен интервал 5 минут с полным обходом канала раз в час. Эти значения можно изменить в `.env`:

```dotenv
POLL_INTERVAL_MINUTES=5
FULL_DISCOVERY_INTERVAL_MINUTES=60
```

При увеличении срока отслеживания растёт число партий статистики, а при увеличении канала — число страниц полного обхода. Автоматического ограничения общего расхода других приложений проект не обеспечивает. HTTP 403 `quotaExceeded` фиксируется в логах; после сброса квоты следующие циклы снова смогут собирать данные. Квота YouTube сбрасывается в полночь по тихоокеанскому времени США.

Официальная документация: [playlistItems.list](https://developers.google.com/youtube/v3/docs/playlistItems/list), [videos.list](https://developers.google.com/youtube/v3/docs/videos/list), [расход квоты](https://developers.google.com/youtube/v3/determine_quota_cost).

## График и сравнение прироста

Выберите видео слева: в общем списке обоих каналов карточки отсортированы по дате публикации, каждая показывает название канала и дату с временем. На графике две линии: голубая — фактические наблюдения, янтарная пунктирная — выбранная аппроксимирующая функция на участке истории и её продолжение в будущее. Вертикальный маркер обозначает последний реальный замер. Наведение показывает точное время и значение. Интерфейс обновляет данные из базы раз в минуту; просмотр страницы не расходует квоту YouTube.

Масштаб меняется кнопками `+`/`−`, сочетанием **Ctrl + колесо** и щипком двумя пальцами на сенсорном экране. Перетаскивание сдвигает график по обеим осям. Кнопка «Сбросить масштаб» и двойной щелчок возвращают полный вид. При обновлении данных и смене интервала выбранный масштаб сохраняется; при выборе другого видео сбрасывается. Масштабирование меняет отображение, расчёты используют полную историю.

Красные пунктирные вертикали отмечают **каждые 24 часа с точного момента публикации**. Для ролика, опубликованного в 19:00 по Москве, первая линия будет на следующие 19:00, затем ещё через сутки. Отметки содержат номер суток и видны как на истории, так и на прогнозе. Это отдельная разметка; графиков данных по-прежнему два.

Сравнение доступно за **1, 2, 3, 4, 6, 8, 12, 24 часа, 2, 3, 4 дня и неделю**. В поле «Свой интервал» можно ввести, например, **13 часов**, в том числе дробное число от 0,01 до 168. Альтернатива — произвольная дата и время **с точностью до минуты**, без секунд и миллисекунд. Базой служит последнее наблюдение **не позже выбранного времени**; его фактическая дата отображается. Рассчитываются прирост просмотров, процент изменения и средняя скорость в час. Дополнительно скорость сравнивается с предыдущим периодом той же длительности, с нормализацией по фактической длине интервалов между замерами. При недостаточной истории или неположительном предыдущем приросте процент изменения скорости не выдумывается.

Карточки «Прирост за интервал» и «Средний прирост / час» также показывают **тот же интервал, сдвинутый на 24 часа назад**. Например, для последних 13 часов берутся 13 часов, закончившиеся вчера в то же время. Доступны вчерашние значения и процент отличия от них; средние скорости учитывают фактическую длительность интервалов между замерами. Используются только реальные наблюдения не позже соответствующих границ, с отставанием не больше двух интервалов сбора. Если нужной истории нет или в ней большой разрыв, сравнение со вчера недоступно. При нулевом или отрицательном вчерашнем приросте процент не рассчитывается. Время базовых вчерашних замеров показано под выбором интервала. Для интервалов длиннее суток сегодняшнее и вчерашнее окна могут пересекаться.

Если выбранное время лежит раньше начала истории, интерфейс сообщает о недостатке данных. Это статистика просмотров; число уникальных зрителей публичный API не предоставляет.

## Аппроксимация и экстраполяция

Можно выбрать горизонт от 1 часа до 7 дней и модель:

| Модель | Функция |
| --- | --- |
| Линейная | `V(t) = a + b · t` |
| Логарифмическая | `V(t) = a + b · ln(1 + k · t)` |
| С насыщением | `V(t) = a + b · (1 − exp(−k · t))` |
| Насыщение + суточный ритм | `V′(t) = b · k · exp(−k · t) · [1 + A · sin(2π · t / 24 + φ)]`, `V(0) = a` |

`t` — часы с первого сохранённого наблюдения. Коэффициенты рассчитываются методом наименьших квадратов, кривизна нелинейных функций перебирается по сетке с уточнением по обучающим данным. Последние 20% точек (минимум 2, при наличии хотя бы 8 наблюдений) откладываются: модели обучаются на предыдущих точках и сравниваются по средней абсолютной ошибке (MAE) на отложенных. Затем коэффициенты выбранной модели пересчитываются на всей истории. Формула, R² и проверочная ошибка доступны в разделе «О модели».

**Суточная модель** изменяет скорость прироста, а на график выводится её интеграл — накопленное число просмотров. Получается насыщение с волнами наклона: время пика `φ` и амплитуда `A` определяются из истории, период фиксирован **24 часа**. Часовой пояс браузера не меняет расчёт и не задаёт аудитории фиксированные «день» и «ночь». Ограничения `b ≥ 0`, `k > 0`, `0 ≤ A ≤ 0,95` сохраняют неотрицательную скорость: кривая растёт и выходит на конечное плато. При `A = 0` это обычная модель насыщения. Синусоида не добавляется напрямую к счётчику, иначе прогноз мог бы периодически терять просмотры.

Для суточной модели нужны **минимум 72 часа истории, 25 замеров и отсутствие разрывов больше 6 часов**. Для обучения должно остаться минимум двое суток и 16 точек, для проверки — минимум полные сутки; последние 20% точек используются, если это даёт более длинную проверку. На такой истории все модели сравниваются на одном и том же отложенном участке. В режиме «Автоматический выбор» суточная модель участвует только при выполнении этих условий. Если более простая модель даёт почти такую же ошибку (`MAE ≤ 1,05 × лучшая MAE + 1 просмотр`), предпочтение получает она; линейная также получает приоритет при почти равной ошибке. Суточную модель можно выбрать вручную. При недостатке истории показывается причина, фактическая линия остаётся доступна. Выученный ритм может измениться; даже несколько циклов не гарантируют точность будущего прогноза.

Для 3–7 наблюдений автоматически используется линейная модель с предупреждением об отсутствии проверки. Нелинейные модели требуют минимум 8 наблюдений. Растущие функции могут выйти на плато; реальные снижения просмотров сохраняются как есть. При короткой истории, большом горизонте или разрыве после последнего наблюдения интерфейс поясняет ограниченность прогноза. Высокое соответствие прошлым точкам не гарантирует точность будущего прогноза.

Прогноз строится на выбранное число часов **после текущего времени**, включая архивные видео. Он является модельной оценкой. Исходные целочисленные значения в базе и сравнениях остаются точными; численное моделирование не выполняется для счётчиков вне безопасного диапазона JavaScript.

### Самостоятельный HTML-отчёт

```sh
npm run report
```

Создаётся `data/report.html`: один файл со встроенными данными, оформлением, графиками и расчётами. Его можно открыть в браузере без сервера и ключа, выбирать видео, даты и интервалы сравнения, модели и горизонт прогноза, масштабировать график, видеть суточные линии и сравнение со вчера, а также скачать CSV. Это снимок на время экспорта; новые наблюдения требуют повторного экспорта. Файл содержит статистику, но не API-ключ.

HTTP API: `GET /api/videos`, `GET /api/videos/:id?compareHours=24&forecastHours=24&model=auto`, сравнение `compareAt=<ISO datetime>` вместо `compareHours` и `GET /api/export.csv`. API читает базу, не запрашивает YouTube и не возвращает ключ. Доступны только GET-запросы; исходники и `.env` не раздаются. Для обновления интерфейса при разработке повторите `npm run build:web`.

## Проверки

Автоматические тесты работают без реального ключа. Они проверяют границу срока и его изменение, историю и перезапуск SQLite, пагинацию и партии API, обработку недоступных видео и ошибок, повторные запросы, отсутствие пересечения циклов и завершение по сигналу. Интеграционный тест использует локальный HTTP-сервер с ответами в формате YouTube API и проходит полный путь от обнаружения видео до записи и экспорта истории.

Для проверки реального канала после настройки ключа выполните `npm run collect`, затем `npm run --silent export`. Если за выбранный период публикаций нет, цикл корректно сохранит ноль наблюдений. Само наличие запущенного процесса ещё не означает успешный сбор: проверьте `collection_completed` и CSV.
